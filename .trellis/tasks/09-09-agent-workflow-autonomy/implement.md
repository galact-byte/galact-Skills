# 实施计划

## 实施前门槛

- [x] 用户同意创建任务；已建立独立任务，不复用旧 H1 或初建 Skill 任务。
- [x] 读取实际全局配置、变更记录、目标 Skill、现有测试入口与相关规范。
- [x] 评估用户补充的七份材料并写入 research/source-assessment.md。
- [x] 用户审阅 prd.md、design.md、implement.md 并明确同意实施。
- [x] implement.jsonl、check.jsonl 含实际规范与调研上下文，task.py validate 通过。
- [x] 用户批准后运行 task.py start，才进入实施。

## 有序步骤

1. 运行 `git status --short` 和 `bash tests/run_tests.sh` 保存基线。已有无关失败单独识别，不覆盖用户改动。
2. 派遣 `trellis-implement`，提示首行为 `Active task: <task.py current 返回路径>`；要求直接实施，不嵌套派遣 implement/check。
3. 按行为分组逐步补充静态回归测试及情景：先运行目标测试观察因旧规则缺失而失败，确认不是语法或路径错误，再更新对应正文并重跑。保留原文件成果，不通过删除 Skill 制造 RED。
4. 在原结构内扩充正文和场景附件，接入 harness 的静态检查计数。新测试用标准库；不污染 README，不新建重复 Skill。
5. 完成后派遣 `trellis-check`，检查需求覆盖、批准清单、冲突措辞、测试的负向敏感性和引用完整性，直接修复发现的问题。
6. 使用可用工具做只读模型情景评估时记录模型、提示、所读 Skill 版本和实际输出；独立于静态 PASS 计数。无真实运行不声称模型行为已验证，不以假想答案代替观察。
7. 最终运行 `bash tests/run_tests.sh`、`python -m unittest discover -s tests -p 'test_agent_workflow.py'`、`git diff --check`，逐项核对验收与整个差异。检查应对应最后一版文件及相关环境。
8. 评估是否有值得更新的 Trellis 规范；没有则记录无需更新，不为填模板而改规范。禁止提交、推送、发布，保留工作区供用户查看。
9. 汇总改动、七份材料的取舍、保留的保障、静态与模型验证范围、未验证项。存在影响验收的缺口时不得标为完成。

## 回归观察点

- 跨文件不等于需要批准；仅要求计划不能写实现，先审方案不能提前实施。
- 未决项仅阻塞依赖，授权外操作必须等明确批准；沉默不授权。
- 普通失败自主诊断，连续失败复核方法；预算或轮次耗尽不能变成通过。
- 严格 TDD 例外守门，任何模式保留既有成果。
- 证据和最终状态匹配，缺少必要环境只可声明本地范围通过。
- 模板交付、PPT 检查点、目标平台运行等领域约束不会被通用规则削弱。

## 保留与恢复

只编辑任务计划列出的文件；实施中发现其他必要变更先核对是否越界。需要撤销时只针对本次可确认的改动做精确替换，不执行 reset/checkout、不覆盖用户后续修改。任务状态在审阅前保持 planning。
