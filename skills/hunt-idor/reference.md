# 对象授权验证参考

## 选择对象与身份

水平验证至少准备自己控制的 A/B 两个账号，各自创建对象并记录归属、可见性、角色和租户。垂直验证需要低权限身份和明确角色预期，不一定需要两个同权限账号。

先保存 A 读 A、B 读 B 的正常响应，再用 A 请求 B 的受控对象。匿名访问是独立对照，不能混用账号凭据。只取足以辨认对象和权限的字段，避免他人数据。

| ID 形式 | 选择候选的方法 | 判定限制 |
|---|---|---|
| 数字 | 使用两个受控对象的已知 ID | 不默认遍历相邻真实用户 |
| UUID | 从自己两个测试账号的创建/列表响应获取 | UUID v4 难猜不等于有授权；UUID v1 的可预测性也不能直接证明越权 |
| Base64 | 在受控副本中解码并替换已知对象标识 | 编码不等于签名，解码结果也不自动被服务端接受 |
| 签名/不透明 ID | 比较跨身份请求与服务端验证结果 | 不能凭长度或外观判断已加密/不可伪造 |

## 语义对照

- 200 可能是自己的数据、公开内容、空数组、登录页或错误 JSON；确认归属、字段和预期权限后再判定。
- 401/403 可能表示请求被拒绝，但写接口仍需在获准范围内核查最终状态，不能只看响应。
- B 明确公开的对象供 A 读取通常不违反权限；公开内容内的额外私有字段需单独判断。
- 无法证实对象归属、租户或预期角色时为 `inconclusive`。缺账号/许可为 `blocked`，不标资产安全。

## GraphQL 与批量接口

按 `node(id:)`、嵌套关联、下载、导出和批量端点分别核对对象级授权。只请求两个受控对象，限制字段、别名和返回体；GraphQL 成功响应中也可能含 errors 或部分数据，需逐项核对。

示意（占位字段须匹配目标 schema）：

```graphql
query {
  user(id: "CONTROLLED_ACCOUNT_B_ID") {
    id
  }
}
```

不存在通用的 `userId != own_id` 自动确认规则：字段可能缺失、类型不同、表示资源而非所有者。不要根据状态码或缺失字段自动输出 confirmed。

## 写入与证据

写入/删除仅在对应动作获准的测试对象上验证，记录初态、修改、清理和结果。保留凭据的完整原始请求只放私有证据；公开报告脱敏。无法清理时停止该方向，不改真实用户对象。
