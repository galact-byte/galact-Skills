# JNDI 判别与运行时参考

## 四层事实

| 层级 | 最小证据 | 仍不能证明 |
|---|---|---|
| 输入可控 | 参数进入日志/配置/lookup 的请求与链路线索 | 已执行命名查询 |
| 网络可达 | 唯一随机标记的 DNS/LDAP/RMI 接收记录 | 一定由目标 JVM 发出，或 lookup 返回了对象 |
| JNDI 查询 | 正反对照与目标日志/调用链等归因证据 | 远程类加载、反序列化、命令执行 |
| 代码执行 | 独立、获准且直接可验证的执行证据 | 任意主机、任意配置都可利用 |

DNS 查询可能由递归解析器发出；LDAP 接收记录也可能来自网关检测。独立标记、时间窗口、基线/阴性对照与目标侧证据共同支撑归因。不要只按回调 IP 判断来源。

## 运行时检查

- 记录 JDK 厂商、精确构建号和回移修补状态；不要用一个“8u191 以上”的区间概括所有现代 JVM。
- 远程 codebase 下载默认值、对象工厂过滤、序列化过滤、可用类路径与具体命名服务实现共同影响结果。
- OpenJDK 的 JDK 24 改动永久禁用了 JNDI LDAP/RMI 远程代码下载，并移除相关 `trustURLCodebase` 开关。这个结论仅针对该功能，不等于禁用所有 JNDI 查询或所有本地对象工厂风险。
- 较旧版本关闭远程类加载不等于所有其他利用路径都成立；序列化对象或本地 factory 的可用性需要具体版本、过滤与类路径证据。本 Skill 不自动尝试 gadget。
- 区分 `log4j-api` 与 `log4j-core`，区分日志消息、MDC/配置、JDBC Appender 等入口；不同 CVE 的前提不同。
- 仅凭依赖文件名不能确定实际加载版本；也不能将扫描器列出的版本风险写成已触发的代码执行。

## 回调设施要求

使用已批准、可控的接收端，确认它不会返回远程类、serialized data 或对象工厂；记录实际监听地址、可达协议、日志时区和保留策略。接收端自测标记与目标标记严格隔离。

每次只发送一个随机不含业务数据的标记。不得嵌入 `${env:...}`、系统属性、用户数据或主机标识；证明出网不需要外带秘密。没有可验证的纯记录模式就停止，不把利用框架默认模式当作安全回调服务。

异步日志可能延迟触发。超过约定窗口记 `inconclusive`，不无限等待或重复发送。修复结论同时核对配置/组件修补与同条件复测，无回调只说明该轮未观察到回调。

## 官方依据

- [Apache Logging Services 安全公告](https://logging.apache.org/security.html)：核对 CVE-2021-44228 与后续相关漏洞各自的组件、版本和触发条件。
- [OpenJDK JDK-8338536](https://bugs.openjdk.org/browse/JDK-8338536)：JDK 24 永久禁用 JNDI 远程代码下载的变更依据。
- [Java InitialContext API](https://docs.oracle.com/en/java/javase/24/docs/api/java.naming/javax/naming/InitialContext.html)：命名上下文和 lookup 的接口语义，不表示任何输入都会执行代码。

修复建议应落在消除不受信任 lookup、升级受影响组件、限制允许的命名协议与目标、最小化出网及合适的过滤策略；不把单个 WAF 规则或远程类加载开关写成完整修复。
