# 竞态条件验证

确认并发请求是否突破后端的唯一性、金额或状态转换规则。**多个 HTTP 200 不等于重复成功；并发响应也不直接证明源码存在某种 TOCTOU 实现。** 方法见 [参考](reference.md)。

## 范围与前提

先落实授权端点、动作、受控账号与对象、可恢复初始状态、总请求预算、并发上限、速率和停止条件。未明确许可金额、库存、短信或密码变更时，不做对应测试；小金额、回滚与测试账号都不能替代动作许可。

从 2 个请求起步，始终不超过双方明确约定的预算。禁止默认 50–100 并发。缺账号、可复位对象、并发许可或合适工具时记 `blocked`，继续其他已具备条件的候选。

## 工作流

### 1. 定义不变量

列出具体操作与规则：限领一次、同一个 token 只能消费一次、库存不能为负、相同幂等键不应产生多笔业务记录。记录规则来源，不从“已有余额不足提示”反推出服务器实现。

区分同一端点、多端点、跨账号和状态机竞争。副作用较大的退款、扣费、密码重置只能在相应沙箱或明确许可的测试对象中验证。

### 2. 串行对照

使用独立测试对象或每轮恢复到可验证的相同初态。记录第一请求、后续重复请求及最终权威状态：业务记录 ID、领取数、账本、库存或 token 的实际状态。

若串行重复也突破规则，先按业务逻辑缺陷调查，不把所有重复操作归为竞态。若无法恢复可比初态，标 `inconclusive`，不能强行比较两轮结果。

### 3. 受控并发

优先使用现场已安装且支持相应功能的 Burp Repeater 请求组或 Turbo Intruder；先核对版本、协议与工具帮助，不自动安装。

- Repeater 的并行发送可用于小组请求，实际同步方式与 HTTP 版本、版本功能有关。
- HTTP/2 单包攻击利用同步释放请求数据降低网络抖动，不保证在所有代理/网络链路中物理上只出现一个包。
- HTTP/1.1 最后字节同步依赖实际请求 framing 与工具实现，不手工套未经验证的脚本。
- 普通线程/异步并发不等于上述同步技术，方法与局限必须写明。

每轮保存并发数、协议、请求、时间窗口、业务响应、初始/最终状态和实际副作用。网络错误、WAF/限流、超时、延迟恶化或异常状态出现时停止，不靠无限加压“撞窗口”。

### 4. 复核与结论

仅在可恢复测试对象、预算和动作许可内复现。以权威最终状态证明重复消费或状态越界；多条相同响应可能只是幂等返回同一记录。等待已约定的异步结算窗口，区分重复显示、排队与真实多笔记录。

- `confirmed`：获准的受控并发可复现地突破明确不变量，串行对照及最终副作用支持归因。
- `candidate`：只有可疑请求、错误或多次成功响应。
- `inconclusive`：状态不可查、初态不可比、未复现或观察窗口不足；未观察到成功不等于不存在竞态。
- `blocked`：许可、对象或工具能力不足。
- `false_positive`：对照已证实为同一幂等结果、显示重复等非规则破坏。
- `out_of_scope`：资产或动作超出授权，停止该方向。

旧记录如使用 `killed`，仅对应已经证伪的具体假设，不表示资产安全或未测项通过。

## 证据门槛与交付

逐项确认：范围及动作许可、不变量、可比初态、串行基线、并发方法与预算、权威最终状态、复现与清理。未满足时保留准确状态，不将全部 NO 归为误报。

记录端点、受控身份、操作与规则、测试对象、串行/并发次数、协议/工具版本、每轮业务 ID 与状态、可量化差值、异步窗口、停止和清理结果、未验证影响。公开报告脱敏；不把理论全站资损写成已经造成的金额。

## 场景自查

1. 2 个 200 返回同一个订单 ID，只有一条账本记录：不能确认为双花。
2. 并发与串行都能重复领券：先调查逻辑/幂等缺陷。
3. 测试对象只能用一次、无法恢复：记录当前证据与限制，不换真实用户对象重试。
4. 小组并发未复现：报告该轮未观察到，不自动升到 100 并发。

相关：业务规则用 `hunt-logic`，对象授权用 `hunt-idor`，一次性令牌设计用 `hunt-auth-bypass`；关联验证仍需满足各自动作许可。
